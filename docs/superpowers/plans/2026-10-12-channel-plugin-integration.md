## 3. 接入前统一的决策

### 3.1 谁负责什么

**本次保持 `owns_commit=True`、`owns_dependency_env=True`。** 我们没有独立环境或另一套 artifact/CAS 事务。仅因为用子进程就设 False，会让 A 拒绝 load/reload/force、跳过目录恢复，并没有得到一个可用的替代安装器。

从 A 的默认 Python 后端中抽出窄的执行策略接缝：

| 接缝（拟新增，不是现有 API） | Python 插件 | 共享进程 Channel |
| --- | --- | --- |
| `describe(source, manifest)` | 现有 backend 与依赖信息 | 静态描述、代码根、依赖文件、展示信息 |
| `probe(candidate)` | 现有宿主 probe | 临时子进程检查依赖及 Driver 入口，返回结果并确认进程退出 |
| `load_definition(description)` | 现有导入得到的插件对象 | 宿主自身构造的轻量登记对象；只登记描述和实例 factory |

轻量登记对象可复用 A 的 `register(api)`、配置重登记与台账。它不是插件包内的旧 `plugin.py`，不会导入平台类。Python 模块快照仅用于宿主 Python 后端；Channel 更新依靠真实旧代码目录与静态记录恢复，不依赖 `sys.modules`。

**探测不得调用 Driver.start。** 当前公共 worker 在握手后会立即启动组件，直接拿 `ChannelProcess.start()` 当 probe 会提前连接平台。需复用 bootstrap 校验的 probe-only 入口，禁止创建正式连接、注册消费者或发送消息。

### 3.2 交付目录采用最小调整

保留 A 的 `<plugins>/<plugin_id>/plugin.json` 安装形状，目录内部把 Python 实现放进一个包：

```text
<plugins>/feishu/                 ← code_root，摘要只覆盖本插件
  plugin.json                    ← 正式关联 channel.json
  channel.json                   ← entrypoint 仍为 feishu.driver:FeishuDriver
  requirements.txt               ← 唯一依赖声明，仍与描述同目录
  README.md
  feishu/
    __init__.py
    driver.py
    platform.py
    ...
```

钉钉使用相同形状。这样既兼容 A 的根目录 requirements 读取，也满足 B 的包导入和描述规则；不用复制依赖清单，不把所有兄弟插件纳入同一个摘要，不让顶层 `platform.py` 遮蔽标准库。配置、媒体、会话及恢复记录始终位于工作区，不进入可替换代码目录。

为 `PluginEntryPoints` 增加显式静态描述入口（建议 `descriptor: "channel.json"`）；有该入口的 Channel 走静态后端，与 `backend: "plugin.py"` 互斥。字段必须进入正式解析和校验，不能依赖现有模型忽略未知字段的行为。`process_mode/dependency_mode` 继续以描述为真相源，不重复维护两份。

运行期间代码根保持稳定；更新复用 A 的先停稳、再切目录。第一版不支持直接覆盖运行中 Channel 源码后的原地热重载：父进程保存旧对象，无法恢复子进程需要重新导入的旧文件。开发更新也通过候选目录进入正常事务。

### 3.3 实例、消息与状态

- 渠道实例身份用稳定的“工作区/Agent 身份 × 渠道键”，不能使用 Workspace 对象地址或每次随机生成的 ID；更新/重启推进 generation，旧回调不能操作新实例。
- 同一个实例只由一条 owner 路径启动；Manager 是使用者，公共 execution 是进程执行者。A 的普通 `spawn_subprocess` 不再次接管同一子进程。
- 宿主消息真正入队后才返回 accepted。`call_soon_threadsafe` 成功仅表示安排了回调，不算接收成功。
- 队列、正在执行的 Agent 与渠道连接分别收尾；进程退出不代表已排队消息或回复完成。未知发送结果不自动补发。
- 安装状态、全局启用、工作区启用、进程就绪、平台连接状态分别表达。核心 ready 已有基础，保留并验证；安装/更新仍需满足其成功条件才能提交，不能用“后台启动中”伪装更新成功。

## 4. 必须处理的实际接缝

| 当前源码中的情况 | 接入要求 |
| --- | --- |
| Loader 不读 channel.json；Registry 只接受类且拒绝官方内置键 | 静态登记 + 官方键唯一归属；失败或停用不能意外把键交给另一个插件 |
| `instantiate_channel` 不提供 LaunchSpec；继承的 clone 也不传它 | 同一宿主 factory 负责首次创建、重启及配置替换 |
| `replace_channel` 先启动新实例再停止旧实例 | 对进程渠道必须先停稳，再启下一代；失败保留旧句柄 |
| 新 workspace 在入表前已有 start_all；重载先启动候选，后停止旧 workspace | 创建、重载、全局卸载必须经过同一 owner；候选准备阶段不得先连同一个机器人 |
| 代理立即 ACK，而真实 Manager 可能稍后拒绝/超时 | 增加可等待的入队结果，按实例代际检查，ACK 后才记去重 |
| 子进程停止结果被压成泛化错误文本 | StopReceipt/状态保留实例、代际、是否退出、强杀及残留信息 |
| 已加载更新与停用重装不同流程；后者可能不 probe | 明确区分“已安装但未验证”和“运行可用”，不能同一成功文案覆盖两者 |
| 依赖锁按 plugin_id、锁失败仍可继续装 | 对实际共享环境加严格锁；拿不到锁不修改环境 |
| 渠道列表只看 available；UI 用 isBuiltin 决定专用表单 | 缺包、停用、失败仍保留配置；专用表单与安装来源解耦 |
| Desktop 冻结包、配套 Python、Docker/wheel 是不同交付边界 | 正式支持代码、元数据、SDK 路径和插件制品必须在各发行形式可见 |
