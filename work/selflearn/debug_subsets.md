# Self-learn：4 条案例开发子集

来源：`episodes.v3.selflearn.jsonl`，146 个 episode，涉及 134 个 PR。

本次逐条检查了全部案例的 AI 结论概况、后续评论/人工 review、提交、reaction 和数据限制，再对入选 8 条阅读 AI 全文和全部可用 diff。只依据这份本地数据，不声称重新访问 GitHub 或执行了评论里报告的历史测试。原始提交对象不在当前本地 Git 中，因此未对历史完整代码做独立复现。

## 文件与正反例含义

| 文件 | 条数 | 用途 |
|---|---:|---|
| `episodes.v3.selflearn.positive4.jsonl` | 4 | 能提出具体、可复用的 Harness 改进假设 |
| `episodes.v3.selflearn.negative4.jsonl` | 4 | 检查分析器是否会在依据不足或 AI 行为获支持时硬造修改 |

每条记录直接复制原始 JSONL 行，没有删减字段、裁剪 diff、修改标签或加入人工答案；8 条来自 8 个不同 PR。说明和预期只写在本文，不作为 Analyze Agent 输入。

这里的正例不等于“用户赞同 AI”，也不等于整条人工反馈都正确；反例不等于“永远不能学习的垃圾数据”，而是当前证据不足以支持纠正性、持久的 Harness 修改。反例可以用于保留正确行为和检查误改。

## 正例：适合提出改进假设

### 1. #6065：删除模块时没有充分核查调用方

`agentscope-ai/QwenPaw#6065:comment-4966350740`

- AI 在 `/agent_output/text` 称 `tool_guard.py` 没有调用方，认可删除该模块，并主要给出低优先级建议。
- `/reviewed_code/diff` 确实删除了模块及其导出；`/post_review_events/1/text` 指出未变更文件 `builder.py` 仍存在延迟导入，并描述 `governor=None` 时的失败路径及 mock 掩盖问题的情况。
- 这是对“无调用方/安全删除”判断的具体间接反证，不必要求人工明确写“AI 错了”才能分析。
- 可优化方向：删除/迁移类任务的调用方搜索步骤、条件分支核查，以及“零引用”结论的证据要求。首选审查 Skill 或任务内验证要求；不能从本数据确定历史工具究竟有没有调用。
- 限制：diff 不含未修改的 `builder.py` 全文，历史调用链来自人工引用；后续应独立回查该版本。不能直接照搬人工提出的权限实现修改。
- **同一人工评论的 P1 不可照单全收**：它称无条件 `pytest.skip()` 使 `importorskip()` 不可达，但 diff 显示 `importorskip()` 位于 `pytest.skip()` 之前。可以讨论重复跳过逻辑，不能采用错误的执行顺序解释。
- `/post_review_events/0/inline_comments` 里的代码注释风格意见应另行分析，不能和运行时崩溃算作同一种缺陷。

### 2. #6203：局部修复未验证调用方如何解释失败

`agentscope-ai/QwenPaw#6203:comment-4998459089`

- AI 认可给 `tasklist` 增加超时及异常处理，只建议调整测试中的常量写法。
- 原始 diff 中探测异常仍 `return False`，测试甚至把这个返回值固化为预期。
- `/post_review_events/0/text` 指出调用方把 `False` 当成“进程已退出”，从而跳过 kill；`/post_review_events/1/text` 给出作者确认、失败断言和修复说明。
- `/post_review_events/2/text`、`/post_review_events/3/text` 又揭示局部探测超时没有受调用方整体预算约束的问题。
- 可优化方向：审查异常返回值时沿调用链核对语义；审查 timeout 时核对整体预算；验证应覆盖真正的上层行为，而不只证明新参数传入成功。
- 需要保留的细节：作者同时确认采用了 AI 的 Low 建议，因此此例既有 AI 遗漏，也有 AI 建议被接受，不能给整个 episode 一个“全错”标签。
- **人工数值也会被纠正**：先前估算约 26 秒，作者报告虚拟时钟复测为 20 秒对 6 秒预算。应说明这个差别；本文未独立运行该复测。

### 3. #6280：消息分段遗漏一种边界

`agentscope-ai/QwenPaw#6280:comment-5022316896`

- AI 称边界语义正确、测试充分、没有问题。
- `/reviewed_code/diff` 的新分段函数只在 `tool_result` 处清空并结算 reasoning，新增测试没有覆盖 `HintBlock` 边界。
- `/post_review_events/0/text` 报告 `Thinking A -> Text A -> HintBlock -> Thinking B -> Text B` 的回归、修复前结果及修复方向；提交记录也对应 hint 分段修复。
- 可优化方向：协议/消息转换类审查要枚举实际边界，核对转换前后的分段是否一致，不能仅凭几个现有测试声称边界全面覆盖。可形成专用核查 Skill，并与 #6203 一起检验“局部测试充分不代表上层语义正确”的假设。
- 限制：这是间接的遗漏证据，不是明确接受 AI 建议。作者提到的“points 2-4”原讨论不在本 episode 中，不能补写其来源。完整历史 formatter 实现及报告中的测试结果仍待独立核实。

### 4. #6069：通用建议忽略当前项目的约束

`agentscope-ai/QwenPaw#6069:comment-4966301944`

- AI 建议把临时 Textual 上界从 `<8.2.9` 放宽到 `<8.3.0` 或 `<9.0.0`，理由是可能与其他依赖冲突。
- 原始 diff 已说明临时锁定与兼容补丁绑定，要等上游修复发布且经 QwenPaw 验证后再移除。
- `/post_review_events/0/inline_comments/0/text` 的人工问题是 `why not ==8.2.8?`，方向是保持更明确的锁定，而不是放宽。
- 可优化方向：提出依赖放宽、兼容性或维护性建议前，先确认 PR 的明确约束和解除条件；项目事实放有范围的知识条目，通用调查步骤放 Skill/Prompt。
- **不是已证明的运行时 bug**：人工是在评论代码，不是明确回复 AI；这是一项有依据的项目意图/建议质量案例。不能因此生成“所有依赖必须精确锁版本”的全局规则，也不能断言所有更新版本都不兼容。

四条的 `diff_status` 都是 `exact`、`confidence` 都是 `medium`、`quality_flags` 都为空。`exact` 表示这份数据记录的比较范围有真实 diff，不等于所有历史定位和人工结论均被独立验证。

前两条是本批最明确的改进线索，第三条补充分段边界，第四条检查项目意图。不要为了凑“重复缺陷”而把四条强行归为同一个根因。第二阶段允许因当前 Harness 已覆盖该问题或缺少历史轨迹而返回 `needs_evidence`，不要求每条都产生 `propose`。

## 反例：不应据此制造 Harness 缺陷

### 1. #7066：有明确反馈，但支持 AI 的具体结论

`agentscope-ai/QwenPaw#7066:comment-5393361381`

- AI 指出 `TokenExchanger` 从二元组改为三元组后，旧的自定义实现会在解包时失败。
- 原始 diff 可核对这个接口变化。`/post_review_events/0/text` 明确要求处理 QwenPaw AI 提出的向后兼容问题，提交说明也明确关联此反馈。
- 预期：识别为对该项建议的直接支持，保留有效的兼容性检查；不能把“用户要求修 PR”误当成“AI 需要被修正”。不能由此推断整个 review 都正确或修复已经独立验证。
- 这也可以限制 #6069 的泛化：不要为避免空泛依赖建议而压制有具体证据的接口兼容性问题。

### 2. #5927：作者回应的是人工要求，后续关闭也不是 AI 失败证据

`agentscope-ai/QwenPaw#5927:comment-4933097678`

- 原始 PR 是为 subprocess 加 `errors='replace'` 的单行改动；AI 认为没有阻塞项。
- `/post_review_events/1/text` 是维护者要求运行 pre-commit，随后作者在 `/post_review_events/2/text` 明确回复 `@xieyxclack`。
- 后续人工说测试失败、引入无关改动，作者决定关闭并重开。不能把这一事件链写成“作者按 AI 建议改坏了代码”，也不能拿后续版本问题反向证明原始单行补丁的评审错误。
- 预期：识别反馈对象和版本限制，不据此提出 Harness 修改；不声称所有后续问题均已核实。

### 3. #6397：点赞是态度，不是具体改进方向

`agentscope-ai/QwenPaw#6397:comment-5090697204`

- `/agent_output/reactions/0` 是针对 AI 消息的 `+1`，应保留且识别为直接正向态度。
- 唯一后续人工 review 是 `LGTM`，它在批准 PR，不等于逐项认可 AI 报告。
- 本例 `reviewed_diff_missing`、`review_snapshot_low_confidence`、`response_changes_unresolved` 均存在。
- 预期：认可存在反馈，但不能据此判断具体 AI 建议正确、更不能提出修改位置。无 diff 时尤其不能把报告中的代码片段当成已核实的历史源码。

### 4. #6681：测试消息和 PR 关闭没有反馈语义

`agentscope-ai/QwenPaw#6681:comment-5177283023`

- diff 只新增一行 `test`，AI 已识别为测试 review bot 的 PR。
- 后续两条评论都是 `test`，之后 closed without merge。
- 预期：可以没有 finding，或说明没有可识别反馈；不能把关闭判为拒绝 AI，也不能从普通测试文字生成“答非所问”等缺陷。
- 账号名含 Bot 但 actor.type 为 human 的原始记录保持不变；不能仅根据名字猜测反馈可靠性。

## Batch 的使用边界

1. `--limit` 是输入条数限制，不是已经实现的 epoch/batch 调度器；目前第一阶段本来就是每条 episode 一个独立会话，第二阶段才跨案例共用新会话。
2. 这两个文件分别提供固定 4 条开发批次，直接 `/analyze` 对应文件即可，不需要额外 `--limit 4`。分别对它们各自的 `episode_analyses.jsonl` 执行 summarize；不要为图方便把两组拼成一个 8 条输入。
3. 小 batch 是控制上下文和费用的起点，不是“越小越准”的保证，也不是数学上真实的梯度更新。后续批次应按 PR 去重，并同时限制输入 token 预算；4 条大 PR 仍可能很长。
4. 按需读取 diff 的现有逻辑保留。本次正例文件约 81 KiB、反例约 29 KiB；文件大小不是实际模型 token 用量或运行时长。
5. 正例批次用于验证能否发现有依据的问题，反例批次用于验证是否会误改。正常迭代可用 3 条相关候选 + 1 条反例组成 4 条批次；不同批次的模式应进入可追溯的历史记录，以免小批丢掉跨批重复问题。
6. 每一步先提出候选，再由独立评测决定是否采用，不要求每批都更新 Harness。这里按已知反馈挑选的 8 条是开发集，不是随机训练样本或盲测集，也不能据其结果估计线上总体收益。
7. 本次只新增数据子集和说明，没有修改 collector、pre-process、Analyze Agent、summarize 或自动优化调度代码；`signal_strength` 的两阶段处理方式保持不变。
